## 1. 计算卡（Device）定义 ——【Fix#2】

本系统 **Device ≠ GPU**。一张卡 = 一个 worker 执行体：
- 阶段1：卡 = ma.exe 本身（串行，capacity=1）
- 阶段2：员工B/C 各一张卡（独立进程或卡内线程池），capacity = MAX_TASKS_PER_CARD(5)

```c
typedef struct {
    int          capacity;    /* 来自角色表；并行卡硬上限 MAX_TASKS_PER_CARD */
    volatile LONG inflight;   /* 在飞任务数。阶段1 直接 ++/--；阶段2 必须 Interlocked* */
    long         ctx_used;    /* 卡级本轮累计估算 tokens，唯一入口 ctx_add() */
    int          calls_left;  /* 卡级本轮模型调用预算，init = MAX_CALLS_PER_ROUND */
} AgentCard;
```
任务→卡的绑定写在任务卡 assignee；卡状态落盘 `blackboard\cards\<card>.json`（进程重启可恢复账本）。

## 2. 上下文的三层参照系 ——【Fix#3】

| 层 | 含义 | 数值来源 | 参与调度？ |
|---|---|---|---|
| L1 会话水位 | 某长对话（如终端进程）的上下文占用。**"60.9% = 974400/1600000"是这一层** | 终端自报 | ❌ 禁止进桌宠调度器（那是别的进程的上下文，写进来就是装饰性死代码） |
| L2 轮次预算 | worker 一轮内累计请求+响应估算 tokens（bytes/3，llm() 记账） | ctx_add() | ✅ 三道水位线的唯一作用对象 |
| L3 单请求 | 一次调用估算输入量 | 派发前检查 | ✅ 红线：输入+预留输出逼近 1.6M×92% 必须先裁剪 |

水位线（相对 1.6M 模型窗口，按卡计）：**75% 黄**=裁剪喂料（判卷只给文件名+各首 4000B）→ **85% 橙**=强制裁剪并记 board.log → **92% 红**=禁新增调用，转 §3 REFUSE 行为。记账只走 `ctx_add(card, delta)`，双向 clamp，禁止裸 `+=`。

## 3. 三道资源闸与触发后行为 ——【Fix#4·a】

闸门只许在 `schedule_task` 一处判；触发后的行为**必须实现，禁止静默返回**：

| 闸 | 条件 | 返回 | 触发后行为 |
|---|---|---|---|
| 坑位 | 并行卡 inflight≥capacity；串行卡见 current_tasks>1 | SCHED_BUSY | 串行>1 = 状态机错误：记断言行并按 BUSY 排队；并行让位重试 ≤2 次，超 → 升级 |
| 配额 | calls_left==0 | SCHED_THROTTLED | 停止新工人/判卷调用；未开始任务标 ESCALATED；**deliver() 仍产出汇总**并带"本轮调用额度用尽"——本轮不算失败 |
| 水位 | ctx_used ≥ 红线 | SCHED_CTX_REFUSE | 强制裁剪后**重试一次**；仍超 → 升级上报，产物文件保留 |
| 非法 | role 越界 / cfg==NULL | SCHED_BAD_ROLE | 记日志退出，不猜默认值（唯一例外：请求帧 role 坏 → 回退主管并记日志） |

## 4. 任务状态机 ——【Fix#4·b】（v1 提了状态机但没给）

```
PENDING → DISPATCHED → SUBMITTED → L1_OK → L2_OK → PASSED
                         │           │      │
                    (L1/L2/L3 失败) ──┴──────┴→ 打回(≤2) / 改写(1次) / ESCALATED
```

| 当前态 | 事件 | 迁移 | 动作 |
|---|---|---|---|
| PENDING | schedule_task OK | DISPATCHED | 任务卡落盘 + board.log |
| DISPATCHED | worker 返回 files[] | SUBMITTED | dynout：实际落盘路径登记进 out[] |
| SUBMITTED | level1（0 token） | L1_OK / L1_FAIL | 纯代码检查 |
| L1_OK | level2 判卷 | L2_OK / L2_FAIL | 计费 1 次；失败原因写回任务卡 review_notes |
| L2_OK | level3 质检 | PASSED / L3_REJECT | 计费 1 次；铁律：criteria 是唯一依据 |
| 任一 FAIL/REJECT | attempts<2 | PENDING（重派） | attempts++，重派前 release+再抢坑 |
| 同上 | attempts==2 | PENDING（改写） | 主管改写卡一次，attempts 清零 |
| 改写后再败 | — | ESCALATED | 进 deliver 上报清单 |

硬约束：每任务 ≤2 打回 + 1 改写；**任务卡 JSON 的 status 字段是唯一真源**（黑板即状态）；任何终态必须 `release_task()` 还坑位。

## 5. 类型定义与调度器签名 ——【Fix#1】

```c
typedef enum { ROLE_MANAGER=0, ROLE_EMP_A, ROLE_EMP_B, ROLE_EMP_C, ROLE_COUNT } AgentRole;
typedef enum { EXEC_SERIAL=0, EXEC_PARALLEL } ExecMode;
typedef enum { SCHED_OK=0, SCHED_BUSY, SCHED_THROTTLED,
               SCHED_CTX_REFUSE, SCHED_BAD_ROLE } ScheduleResult;
```
角色表 `static const AgentConfig g_role_tbl[ROLE_COUNT]` 是唯一真源，配 `typedef char tbl_check[...]` 编译期断言。

v1 的 `schedule_task(AgentRole)` 不可实现——缺账本、预算、状态三类输入。完整签名：
```c
ScheduleResult schedule_task(AgentConfig *cfg, AgentCard *card, Task *t);
/* 内部按序：状态合法性(§4 switch default) → 坑位 → 配额 → 水位；
   放行时完成 calls_left-- 、抢坑、t->status=DISPATCHED —— 副作用收进闸门，调用方没有"忘了改状态"的机会 */
void release_task(AgentCard *card, Task *t);   /* 终态必调；阶段2 InterlockedDecrement */
```
阶段2 抢坑（禁止 check-then-act）：
```c
LONG n = card->inflight;
for (;;) {
    if (n >= card->capacity) return SCHED_BUSY;
    if (InterlockedCompareExchange(&card->inflight, n+1, n) == n) break;
    n = card->inflight;
}
```
容量映射：MANAGER/EMP_A 串行卡 **capacity=1**（v1 表里给 A 配 5 是把串行语义和并行上限混写，v2 订正：5 是并行卡的上限）；EMP_B/C=5、enabled=0（阶段1）。

## 6. 菜单与切换语义

- 角色 radio 切换**对下一请求帧生效**；在飞轮次按已发出帧跑完，不回收不中途改（避免半主管半员工）。
- 灰显项由 UI 挡手 + §3 闸门挡程序化硬发，**双保险缺一都算没实现**（已实测：role=2 直灌 0.91s 零调用被拒）。
- 容量/配额/水位数值只许改 §5 头文件常量，业务分支里出现字面量即评审打回。

## 7. 应用场景分流（保留 v1，正确）

- 陪聊 → 本地管道：独立进程、共享记忆注入、近谈 8 轮，**不占卡不占配额**。
- 做事 → 多智能体：走 §3/§4 全闸，单轮 3~8 次调用，十几秒~几十秒。
